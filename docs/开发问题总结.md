## 为什么选择 WSL 开发环境

**对应文件**: `web/app.py`, `Makefile`

### 原因分析

1. **工具链兼容性**：Flex、Bison、NASM、GCC 等编译工具在 Linux 下有更好的支持和稳定性
2. **跨平台测试**：项目最终需要在 Linux 环境下运行，WSL 提供了原生 Linux 环境
3. **Windows 便利性**：保留 Windows 的 IDE 和图形界面优势，同时使用 Linux 工具链
4. **团队协作**：统一开发环境，减少"在我电脑上能跑"的问题

### 实现方式

```python
# web/app.py 中的跨平台检测
import platform

is_windows = platform.system() == 'Windows'

if is_windows:
    # 通过 WSL 调用编译器
    cmd = f'wsl bash -c "cd {wsl_path} && ./compiler temp.c"'
else:
    # 直接调用
    cmd = './compiler temp.c'
```

## 问题 1：堆栈溢出问题

**对应文件**: `scripts/asm_generator.py`

### 问题描述

运行时出现 Segmentation Fault，或输出垃圾值。

### 现象

- 简单程序正常运行
- 变量较多时程序崩溃
- 数组访问结果错误

### 原因分析

1. 变量偏移从 4 字节改为 8 字节后，栈空间使用增加
2. 原始栈帧大小仅 144 字节，不足以容纳所有变量
3. 数组分配未预留足够空间，后续变量覆盖数组元素

### 解决方案

```python
# 扩展栈帧大小
result += [tab + "sub rsp, 1024"]  # 原来是 144

# 数组分配时预留空间
num_slots = (size + 3) // 4
for _ in range(num_slots):
    data[data.index(-1)] = f"__arr_reserved_{arr_name}_{_}"
```

### 收获

- 栈帧大小应根据程序复杂度动态计算
- 数组和普通变量需要分区管理

## 问题 2：Windows/Linux 编码转换问题

**对应文件**: `web/app.py`

### 问题描述

Web 界面在 Windows 上运行 Flask，但编译工具链在 WSL 中。项目路径包含中文，导致：
- subprocess 调用失败或乱码
- 文件找不到（路径不一致）
- WSL 输出的网络警告干扰编译日志

### 解决方案

#### 1. 统一编码

```python
# 所有 subprocess.run 使用 UTF-8 编码
result = subprocess.run(
    cmd,
    encoding='utf-8',
    errors='replace',
    capture_output=True
)
```

#### 2. 统一路径

```python
def win_to_wsl_path(win_path):
    """将 Windows 路径转换为 WSL 路径"""
    # C:\Users\... → /mnt/c/Users/...
    if ':' in win_path:
        drive, rest = win_path.split(':', 1)
        return f"/mnt/{drive.lower()}{rest.replace(chr(92), '/')}"
    return win_path
```

#### 3. 过滤 WSL 噪音

```python
def filter_wsl_warnings(output):
    """过滤 WSL 的网络警告等无关输出"""
    filtered = []
    for line in output.split('\n'):
        if 'wsl:' in line.lower():
            continue
        if 'localhost' in line and 'NAT' in line:
            continue
        if '\ufffd' in line:  # 乱码字符
            continue
        filtered.append(line)
    return '\n'.join(filtered)
```

### 收获

- 跨平台开发中编码和路径是最基础也最容易出问题的地方
- 在系统最外层"定死"统一的工作目录和字符编码
- 适当过滤第三方环境噪音能提升用户体验

## 问题 3：内存泄漏问题（Valgrind）

**对应文件**: `src/utils/tree.c`, `src/frontend/yacc.y`

### 问题描述

使用 Valgrind 检测发现大量内存泄漏，主要集中在 AST 节点和字符串分配。

### 现象

```
==12345== LEAK SUMMARY:
==12345==    definitely lost: 8,192 bytes in 256 blocks
==12345==    indirectly lost: 16,384 bytes in 512 blocks
```

### 原因分析

1. `createTree` 分配的节点未释放
2. `mergeCode` 生成的字符串未释放
3. 符号表中的字符串未管理

### 解决方案

#### 1. AST 节点释放

```c
void freeTree(Tree* node) {
    if (node == NULL) return;
    
    // 释放子节点
    for (int i = 0; i < node->num; i++) {
        freeTree(node->leaves[i]);
    }
    
    // 释放字符串
    if (node->content) free(node->content);
    if (node->name) free(node->name);
    if (node->code) free(node->code);
    
    // 释放节点本身
    free(node->leaves);
    free(node);
}
```

#### 2. 编译结束时统一释放

```c
// 在 main 函数末尾
freeTree(ast_root);
freeSymbolTable(symbol_table);
```

### 收获

- 编译器虽然是短生命周期程序，但内存管理仍然重要
- Valgrind 是检测内存问题的有效工具
- 采用统一的内存管理策略（如 Arena 分配器）可简化释放逻辑

## 问题 4：最长优先级（关键词优先）

**对应文件**: `src/frontend/lex.l`

### 问题描述

标识符如 `integer` 被错误识别为关键字 `int` 加上 `eger`。

### 现象

```c
int integer = 10;  // 错误：'eger' 未定义
```

### 原因分析

Flex 默认采用最长匹配原则，但关键字和标识符的规则顺序也影响匹配结果。

### 解决方案

#### 1. 关键字规则放在标识符之前

```flex
/* 关键字（必须放在标识符之前） */
"int"       { return INT; }
"float"     { return FLOAT; }
"if"        { return IF; }
"else"      { return ELSE; }
"while"     { return WHILE; }
"for"       { return FOR; }
"return"    { return RETURN; }
"void"      { return VOID; }

/* 标识符（放在关键字之后） */
{LETTER}({LETTER}|{DIGIT})*   { return ID; }
```

#### 2. 确保关键字模式精确匹配

关键字使用字面量字符串匹配，不会匹配更长的标识符。Flex 会优先选择最长匹配，因此 `integer` 会匹配标识符规则而非 `int` 关键字。

### 收获

- 词法分析中规则顺序很重要
- 最长匹配原则确保关键字不会错误匹配标识符前缀
- 测试时应包含边界情况（如以关键字开头的标识符）

## 问题 5：mergeCode 可变参数导致段错误

**对应文件**: `src/frontend/yacc.y`, `src/utils/tree.c`

### 问题描述

`mergeCode` 是可变参数函数 `mergeCode(n, code1, code2, ...)`，用于拼接中间代码片段。随着语法扩展，参数个数容易写错。

### 现象

- 编译通过但运行时 Segmentation fault
- 只打印 `read successfully` 后崩溃
- 中间代码生成不完整

### 原因分析

C 语言的可变参数函数不检查参数个数。若 `n` 与实际参数不匹配，运行时会"错位取参"，严重时直接崩溃。

### 解决方案

#### 1. 系统性梳理

逐条检查所有与函数、数组、指针相关的 `mergeCode` 调用，确保 `n` 与后面参数个数完全一致。

#### 2. 调试方法

```c
// 在纸上画出中间代码片段的拼接过程
// 再翻译成 mergeCode 调用
// 避免"凭感觉写"

// 示例：生成 if 语句中间代码
// if (cond) { body } else { else_body }
// 
// 需要拼接：
// 1. cond_code
// 2. "if " + cond_result + " goto " + then_label
// 3. "goto " + else_label
// ...

$$->code = mergeCode(7,       // 确保是 7 个参数
    $3->code,                  // 1. 条件代码
    "#if ", $3->inner,         // 2. if 指令
    " goto ", then_label,      // 3. 跳转目标
    "\n"                       // 4. 换行
);
```

#### 3. 未来改进

考虑用数组或结构体传递序列，或封装成 `merge2`、`merge3` 等固定参数函数。

### 收获

- 可变参数函数缺乏编译期保护，运行时易崩溃
- 对关键基础设施，应尽量避免滥用可变参数
- 添加调试输出可以快速定位问题

## 问题 6：IR 设计中的行号管理

**对应文件**: `src/frontend/yacc.y`, `src/utils/inner.c`

### 问题描述

在生成中间代码时，控制流语句（如 `if-else`、`while`）依赖行号作为跳转目标。早期实现中，每个函数定义结束后会重置 `line_count = 1`，导致多函数程序的中间代码行号重复，跳转目标错乱。

### 现象

- 程序执行路径不正确（该走 else 却走了 if）
- 循环次数异常
- nasm 报告某些标签未定义

### 原因分析

1. 在 `yacc.y` 的 `project` 规则中，错误地在每个 `external_declaration` 后重置行号
2. `if/while` 的行号计算逻辑不严谨，偏移量不准确

### 解决方案

#### 1. 全局唯一行号

只在编译开始时初始化 `line_count = 1`，整个程序行号全局递增。

#### 2. 使用符号标签系统

```c
// yacc.y 中使用符号标签而非硬编码行号
int label_id = 0;

while_expression
    : WHILE { 
        // 生成唯一标签
        char* start = malloc(32);
        char* end = malloc(32);
        sprintf(start, "WHILE_%d_START", label_id);
        sprintf(end, "WHILE_%d_END", label_id++);
    }
    '(' expression ')' statement
    {
        $$ = whileOpr("while", start, end, $4, $6);
    }
;
```

#### 3. 标签替换

```c
// inner.c 中的 replaceLabels 函数
void replaceLabels(char *code) {
    // 第一遍：收集标签定义及其对应行号
    // 第二遍：替换 goto @LABEL 为 goto 行号
    // 第三遍：删除标签定义
}
```

### 收获

- 中间代码行号是控制流正确性的"单一真相来源"
- 任何地方的"偷懒复用/重置"都会在远处体现
- 使用显式标签名比自然数行号更健壮
