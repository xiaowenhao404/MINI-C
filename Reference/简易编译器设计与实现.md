# 编译原理课程设计：基于 Mini-C 的优化编译器设计与实现综合研究报告

## 1. 执行摘要与项目愿景

本报告旨在为编译原理课程设计提供一份详尽的、专家级的实施蓝图。项目的核心目标是构建一个名为 "Mini-C" 的简易但功能完备的编译器，该编译器不仅能够处理 C 语言的核心子集，还集成了诸如浮点运算、结构体处理、多维数组及指针等高级特性。更为关键的是，本项目将通过引入**活跃性分析（Liveness Analysis）\**驱动的栈空间复用优化、\*\*常量折叠\*\*以及\**死代码消除**等技术，展现出超越常规课程设计要求的创新性与技术深度。

针对用户提出的基于 `xiaowenhao404/c-compiler-master` 进行二次开发的需求，本报告进行了深入的可行性评估。虽然该基础库提供了一个起步框架，但为了满足本项目提出的 21 项功能需求及 3 项高级需求，特别是涉及中间代码生成（IR）和后端优化的部分，必须对其架构进行根本性的重构。本报告推荐采用**多遍扫描（Multi-Pass）**架构，将词法分析、语法分析、语义分析、中间代码生成、优化及目标代码生成严格分层。

此外，为了增强系统的教学价值与交互性，本报告详细设计了一个集成化的开发环境（IDE）外壳，利用 Python/Web 技术栈封装底层 C 编译器，实现了语法高亮、AST 可视化、FIRST/FOLLOW 集自动计算展示等高级功能。这将使得编译器内部复杂的运作机制——如符号表的演变、活跃变量的生命周期——以直观的方式呈现给用户。

## 2. 架构设计与文件结构重构

### 2.1 设计哲学：从玩具到工具的跨越

在编译器的设计光谱中，一端是像 `TCC` (Tiny C Compiler) 这样的单遍扫描编译器，它追求极致的编译速度，在解析语法的同直接生成机器码 1；另一端则是像 `LLVM` 或 `GCC` 这样基于 SSA（静态单赋值）形式的工业级编译器，具备强大的优化能力。

针对本课程设计，为了实现**可行性**（在有限时间内完成）与**创新性**（实现活跃性分析优化）的最佳平衡，我们摒弃单遍扫描模式，转而采用一种**保留高层语义的线性中间表示（Linear IR）**架构。

- **前端（Frontend）：** 负责构建抽象语法树（AST），处理类型检查（Type Checking）和语义验证。
- **中端（Middle-end）：** 将 AST 降级为四元式（Quadruples），在此层面上执行与机器无关的优化（如常量折叠、死代码消除）。
- **后端（Backend）：** 负责活跃性分析，据此进行栈槽分配（Stack Slot Allocation），最终生成 x86-64 汇编代码。

## 3. 前端实现：词法与语法分析的深度扩展

### 3.1 词法分析（Lexical Analysis）的增强

基础的词法分析器通常仅支持整数和基本符号。为了满足需求 1（实型数据）、需求 10（注释）及需求 13（字符串），我们需要显著增强状态机的逻辑。

#### 3.1.1 浮点数识别机制（需求 1）

词法分析器需引入前瞻（Lookahead）逻辑来区分整数与浮点数。

- **逻辑流：** 当读取到数字序列时，暂不立即生成 Token。检查后续字符是否为小数点 `.`。
  - 如果是 `.`，则继续读取后续数字，生成 `TK_FLOAT` 类型 Token。
  - 需同时支持科学计数法（如 `1.2e-3`），这要求状态机能处理 `e` 或 `E` 及其后的符号位 `+` / `-`。
- **数据存储：** 对于 `TK_FLOAT`，其值不能仅存为 `int`，需要在 Token 结构体中引入 `union` 来存储 `double` 值 2。

#### 3.1.2 注释处理（需求 10）

支持单行注释 `//` 和多行注释 `/*... */` 需要在 `next_token` 函数入口处增加预处理逻辑。

- **单行注释：** 检测到 `//` 后，循环消耗字符直至遇到换行符 `\n`。
- **多行注释：** 检测到 `/*` 后，进入死循环模式消耗字符，直到匹配到 `*/`。此处需注意，标准 C 语言不支持嵌套注释，实现时应遵循此规范以简化逻辑。

#### 3.1.3 字符串与字符字面量（需求 11, 13）

- **字符串池（String Pool）：** 编译器遇到字符串字面量（如 `"Hello"`）时，不能直接丢弃内容。必须将其添加到一个全局的字符串表中，并返回一个指向该表项的标签（Label，如 `.LC0`）。在代码生成阶段，这些字符串将被发射到汇编的 `.rodata` 段。
- **转义字符：** 必须解析 `\n`, `\t`, `\0` 等转义序列，将其转换为对应的 ASCII 码值存储。

### 3.2 语法分析（Syntax Analysis）与 AST 构建

语法分析器将 Token 流转换为 AST。为了支持复杂的表达式（需求 9）和结构体（需求 5），推荐使用**递归下降分析法（Recursive Descent Parsing）**，因为它易于手动实现且直观对应 EBNF 文法 。

#### 3.2.1 结构体与类型定义的解析（需求 5）

结构体的引入是本次设计的难点之一。我们需要在语法分析阶段构建类型表。

- **文法规则：**

  EBNF

  ```
  struct_decl ::= "struct" IDENTIFIER "{" member_list "}" ";"
  member_list ::= declaration ";" { declaration ";" }
  ```

- **内存布局计算：** 当解析 `struct` 内部成员时，编译器必须实时计算每个成员相对于结构体起始地址的**偏移量（Offset）**。

  - 例如：`struct { char a; int b; }`。`a` 偏移 0。由于 `int` 通常需要 4 字节对齐，`b` 的偏移量可能不是 1，而是 4（取决于对齐策略，建议简化为紧凑排列或固定 8 字节对齐以降低难度）。
  - 这些元数据（成员名、类型、偏移量）必须存储在 AST 的 `Type` 节点中，供后续语义分析使用 5。

#### 3.2.2 数组与指针的解析（需求 3, 4）

- **多维数组：** `int a`。解析时是从左向右结合，但在类型构建上是递归的：`Array(3, Array(4, Int))`。

- **指针：** `int **p` 解析为 `Pointer(Pointer(Int))`。

- **AST 节点设计：**

  C

  ```
  struct Type {
      enum { TY_INT, TY_FLOAT, TY_PTR, TY_ARRAY, TY_STRUCT } kind;
      struct Type *base;      // 指针或数组的基类型
      int array_size;         // 数组大小
      struct Member *members; // 结构体成员链表
      int size;               // 类型总大小（字节）
  };
  ```

#### 3.2.3 表达式优先级的处理（需求 8, 9, 15）

为了支持带括号的混合运算及关系运算符，解析器函数必须分层调用：

1. `equality()`: 处理 `==`, `!=`
2. `relational()`: 处理 `<`, `<=`, `>`, `>=`
3. `add()`: 处理 `+`, `-`
4. `mul()`: 处理 `*`, `/`
5. `unary()`: 处理 `&`, `*`, `+`, `-`, `!`
6. `primary()`: 处理 `()`, 标识符, 字面量

这种层级调用天然地保证了运算优先级：`mul` 会先于 `add` 被结合。

## 4. 语义分析与类型检查

在生成代码前，必须验证程序的逻辑合法性，并进行必要的隐式转换。

### 4.1 类型提升（Type Promotion）（需求 1）

C 语言标准规定，当 `int` 和 `float` 进行运算时，`int` 必须隐式转换为 `float`。

- **实现逻辑：** 在构建二元运算 AST 节点（如 `ND_ADD`）时，检查左右子节点的类型。
  - 如果 `LHS` 是 `int`，`RHS` 是 `float`，则在 `LHS` 上方插入一个 `ND_CAST` 节点，目标类型为 `float`。
  - 这确保了后端生成指令时，使用的是浮点加法指令（如 `addss`）而不是整数加法。

### 4.2 左值与指针退化

- **数组退化（Decay）：** 在大多数表达式中，数组名 `a` 应被视为指向首元素的指针。语义分析器需识别 `ND_VAR` 节点若为数组类型，则将其转换为 `ND_ADDR` 节点（除非是 `sizeof` 操作数）。
- **指针运算：** 对于 `ptr + 1`，如果 `ptr` 是 `int*`，实际增加的地址值不是 1，而是 `1 * sizeof(int)`。语义分析器必须将 AST 中的 `+ 1` 重写为 `+ (1 * 4)`。

## 5. 中间代码生成（四元式）

为了支持高级优化（如活跃性分析），直接从 AST 生成汇编是不够的。我们需要生成一种线性的中间表示（IR），通常采用四元式（Quadruples）形式：`op, arg1, arg2, result`。

### 5.1 IR 设计

- **算术运算：** `ADD t0, a, b` 表示 `t0 = a + b`。
- **控制流：** `JMP label`, `BEQ t0, 0, label`（若 t0 为 0 则跳转）。
- **函数调用：** `PARAM a`, `CALL f, n`.

### 5.2 流程控制的翻译（需求 15）

针对 `if (cond) { A } else { B }`，翻译策略如下：

1. 生成计算 `cond` 的代码，结果存入临时变量 `t`。
2. 生成 `BEQ t, 0, L_ELSE` （若条件为假，跳到 Else 块）。
3. 生成 A 代码块。
4. 生成 `JMP L_END`。
5. 插入标签 `L_ELSE:`。
6. 生成 B 代码块。
7. 插入标签 `L_END:`。

这种线性化结构是构建控制流图（CFG）的基础，而 CFG 是进行活跃性分析的前提。

## 6. 核心创新与优化策略

此部分是本项目满足“创新性”要求的核心。我们将实现三个关键优化，特别是基于活跃性分析的栈空间复用。

### 6.1 优化一：活跃性分析与栈槽复用（创新点，需求 18）

背景： 在朴素的编译器中，每个临时变量（AST 中的中间节点）都会在栈帧中分配一个独立的槽位。对于复杂的表达式，这会导致栈空间急剧膨胀。

目标： 通过分析变量的生命周期，让不相交（即不会同时存活）的变量复用同一个栈槽。

算法实现步骤 7：

1. **构建控制流图（CFG）：** 将线性 IR 划分为基本块（Basic Block），每个基本块包含顺序执行的指令序列，仅在末尾有跳转。

2. **计算 Use/Def 集合：** 对每个基本块，确定哪些变量在赋值前被使用（Use），哪些变量被赋值（Def）。

3. **数据流迭代求解：** 使用反向数据流方程计算每个基本块入口（IN）和出口（OUT）的活跃变量集合。

   - $$OUT = \bigcup_{S \in succ(B)} IN$$

     ​    \*  

     $$IN = USE \cup (OUT - DEF)$$

   - 重复迭代直至集合不再变化（不动点算法）。

4. **构建干涉图（Interference Graph）：** 图中的节点是变量。如果在某个程序点，两个变量同时活跃（都在活跃集合中），则在它们之间连一条边。

5. **栈槽着色（Stack Slot Coloring）：** 这是一个图着色问题的简化版。

   - 遍历所有变量。为每个变量分配一个栈偏移量（Offset）。
   - 如果变量 A 和变量 B 没有边连接（即不干涉），则它们可以共享同一个 Offset。
   - **实现：** 维护一个 `FreeOffsets` 列表。当处理变量 V 时，检查其相邻节点已占用的 Offset，选择一个未被占用的最小 Offset。

**成果展示：** 在文档中，通过表格列出优化前后的栈帧大小对比。例如，优化前 `sub rsp, 128`，优化后 `sub rsp, 48`，证明了活跃性分析的有效性。

### 6.2 优化二：常量折叠（Constant Folding）（需求 19）

**实现逻辑：** 这是一个在 AST 层面的遍历优化 10。

- 定义递归函数 `fold(Node *node)`。
- 对于二元运算节点（如 `ND_ADD`），递归调用 `fold` 处理左右子树。
- 检查：如果 `node->lhs` 和 `node->rhs` 均为数字字面量节点（`ND_NUM` 或 `ND_FLOAT_LIT`）：
  - 执行计算（如 `3 + 4`）。
  - 将当前节点替换为包含结果 `7` 的新叶子节点。
  - **注意：** 需处理浮点数折叠和除零异常。

### 6.3 优化三：死代码消除（DCE）（需求 20）

**实现逻辑：** 结合常量折叠进行。

- 在解析 `if (cond) stmt` 结构时，如果 `cond` 经折叠后为常数 `0`，则直接丢弃 `stmt` 对应的 AST 子树，不生成任何代码。
- 如果 `cond` 为常数 `1`，则仅保留 `stmt`，去除 `if` 分支结构。
- 更高级的 DCE 可以在 IR 层面通过“不可达代码分析”实现：从 CFG 的入口节点开始遍历，无法到达的基本块直接剔除。

## 7. 后端：x86-64 汇编生成

后端负责将 IR 映射到具体的机器指令。

### 7.1 函数调用规范（ABI）与栈帧管理

遵循 System V AMD64 ABI（Linux）或 Windows x64 调用约定。

- **参数传递：** 前 6 个整型参数通过寄存器 `rdi, rsi, rdx, rcx, r8, r9` 传递，浮点参数通过 `xmm0-xmm7` 传递。多余参数压栈。
- **栈对齐：** 在 `call` 指令执行前，栈指针 `rsp` 必须 16 字节对齐。代码生成器需在序言（Prologue）中计算所需的填充字节。

### 7.2 浮点数指令生成（需求 1）

x86-64 使用 SSE 指令集处理浮点数。

- **加载/存储：** `movss` (Move Scalar Single-Precision)。
- **运算：** `addss`, `subss`, `mulss`, `divss`。
- **比较：** `ucomiss`。比较结果会影响 EFLAGS 寄存器，后续可使用 `ja`, `jb` 等指令跳转。
- **类型转换：** `cvtsi2ss` (Int -> Float), `cvttss2si` (Float -> Int)。

### 7.3 I/O 与 Printf 支持（需求 11, 14）

由于我们是编写 C 编译器，可以直接链接系统的 `libc`。

- 对于 `printf` 调用，除了设置 `rdi`（格式字符串）和 `rsi` 等参数外，**必须**将 `rax` 寄存器设置为使用的向量寄存器数量（浮点参数个数）。这是一个常被忽略的细节，导致 printf 打印浮点数崩溃。

## 8. 高级需求实现方案

### 8.1 FIRST 集与 FOLLOW 集自动求解（高级需求 1）

为了将理论与实践结合，我们将在编译器中内置一个文法分析工具。

算法实现 12：

1. **数据结构：** 定义 `Symbol` 结构和 `Rule` 结构来表示文法产生式。
2. **FIRST 集计算：**
   - 初始化所有非终结符的 FIRST 集为空。
   - 对于产生式 $X \rightarrow Y_1 Y_2...$，若 $Y_1$ 是终结符，加入 $FIRST(X)$。若 $Y_1$ 是非终结符，将 $FIRST(Y_1) \setminus \{\epsilon\}$ 加入 $FIRST(X)$。如果 $Y_1$ 可推导为空，则继续处理 $Y_2$。
   - 重复扫描直到集合不再增大。
3. **FOLLOW 集计算：**
   - 将 `$` 加入起始符号的 FOLLOW 集。
   - 对于 $A \rightarrow \alpha B \beta$，将 $FIRST(\beta) \setminus \{\epsilon\}$ 加入 $FOLLOW(B)$。
   - 若 $\beta$ 可推导为空，或产生式末尾即为 $B$，则将 $FOLLOW(A)$ 加入 $FOLLOW(B)$。
4. **展示：** 编写一个函数，格式化打印所有非终结符的 FIRST/FOLLOW 集合表格。

### 8.2 可视化编译器界面（高级需求 2, 3）

为了避免使用 `cat` 命令查看中间结果的尴尬，建议开发一个基于 Python Flask 的 Web 界面作为编译器外壳 15。

**实现方案：**

- **Web 前端（HTML/JS）：** 使用 `CodeMirror` 实现带有 C 语言语法高亮的代码编辑器。右侧分为四个 Tab 页：Tokens, AST, IR (Quadruples), Assembly。
- **Python 后端：**
  - 接收前端代码，保存为 `temp.c`。
  - 调用编译器：`./minic -dump-tokens -dump-ast -dump-ir temp.c`。
  - 编译器将各阶段的中间结果输出到不同的临时文件或标准输出流。
  - Python 捕获这些输出并返回给前端展示。
- **高亮显示：** 汇编代码可以使用简单的正则高亮，使寄存器和指令更清晰。

## 10. 结论

本设计方案通过引入多遍扫描架构和线性 IR，成功打破了传统简易编译器的功能天花板，使得实现结构体、浮点数以及活跃性分析等高级特性成为可能。特别是栈槽复用优化，不仅满足了课程设计中对于“创新性”的高要求，也让学生深入理解了编译器后端资源分配的核心逻辑。配合可视化的 Web 界面，本项目将成为一份兼具理论深度与工程实践价值的优秀课程设计作品。
